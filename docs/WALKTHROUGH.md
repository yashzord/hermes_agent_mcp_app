# Recall - a guided walkthrough

For **you, the author**, six months from now - or anyone who wants to understand
every layer, not just the map. `architecture.md` is the one-page map; this is the
slow, annotated tour with the *why* behind each line.

Read alongside the flow diagram:
[MCP Apps flow (artifact)](https://claude.ai/code/artifact/efc2e82b-b1d1-480f-a5ca-874083098027).

---

## 1. What you actually built

**Recall** is a spaced-repetition flashcard app - but it has no website and no app
store. It lives *inside a chat client* as an **MCP server**. You talk to it in
plain language ("quiz me"), and when it shows you a card, that card is a real,
clickable widget rendered right in the chat: tap to flip, tap a grade button, and
the next card appears.

So there are really three things in this repo:

1. **A normal little backend** - SQLite database, some functions, a scheduling
   algorithm. Nothing exotic.
2. **An MCP wrapper** - that exposes those functions as *tools* an AI client can call.
3. **An MCP App (widget)** - a self-contained HTML page the client renders as an
   interactive card.

Most of the code is #1. #2 is a few lines of wiring. #3 is one HTML file. That's
the whole thing.

---

## 2. The three ideas you need first

### MCP (Model Context Protocol)
A standard way for an AI client (Claude, MCPJam, etc.) to discover and call your
server's **tools**, **resources**, and **prompts** over JSON-RPC. Think "REST for
LLM clients," but the client's *model* decides when to call each tool.
Live docs: <https://modelcontextprotocol.io>

### MCP Apps (the `ext-apps` extension)
An extension on top of MCP that lets a server ship a **prebuilt UI** as a
resource. A tool result can point at that UI, and a supporting client renders it
in a **sandboxed iframe**. The iframe talks back by calling more tools. This is
the part that makes a *widget* instead of a wall of text.
FastMCP (the Python library you used): <https://gofastmcp.com>

> Key idea you asked about: **the UI is prebuilt by you, not generated by the LLM.**
> The model only decides to *call the tool* that's linked to the UI. After the
> widget appears, your clicks call tools directly through the host - the model is
> out of the loop.

### SM-2 (the scheduling math)
The classic spaced-repetition algorithm (the SuperMemo/Anki family). Each card
carries an **ease factor** and an **interval** (days until you see it again).
Grade a card and the algorithm stretches or resets that interval. Background:
<https://en.wikipedia.org/wiki/SuperMemo> and the Anki manual's
"What spaced repetition algorithm does Anki use?".

## 3. The file map

| File | Job | One sentence |
|------|-----|--------------|
| `server/src/sm2.py` | scheduling math | Pure function: given a grade, return the new ease + interval. No I/O. |
| `server/src/state.py` | storage | SQLite `cards` + `reviews` tables; calls `sm2.schedule`. |
| `server/src/seed.py` | starter data | ~20 cards loaded the first time the DB is empty. |
| `server/src/tools/*.py` | the MCP tools | One thin function each: `ping`, `add_card`, `review_next`, `grade_card`, `stats`. |
| `server/src/server.py` | wiring | Registers tools + the UI resource, picks the transport. |
| `server/src/ui/flashcard.html` | the widget | Self-contained HTML/CSS/JS card; talks to the host over postMessage. |
| `server/tests/` | tests | Pure SM-2 tests + SQLite integration tests. |
| `render.yaml`, `server/Dockerfile` | deploy | Build the container, run it on Render over HTTP. |

The design rule: **each layer knows only the layer below it.** The widget doesn't
know about SQLite. `sm2.py` doesn't know a database exists. That separation is why
each piece is easy to test and reason about.

## 4. Code walkthrough, bottom up

We go from the innermost, dumbest layer (pure math) outward to the widget.

### 4.1 `sm2.py` - the math, and nothing else

```python
def schedule(ease, interval, review_number, rating):
    if rating == CardRating.AGAIN:
        interval = 1            # got it wrong -> see it again tomorrow
        ease = ease - 0.2       # and make it "harder" (shorter future gaps)
    else:
        if review_number <= 1:  # first time graded: fixed small intervals
            interval = {GOOD: 1, EASY: 4, HARD: 1}[rating]
        elif rating == HARD:
            interval = max(1, int(interval * 1.2))
        elif rating == GOOD:
            interval = int(interval * ease)     # grow by the ease factor
        elif rating == EASY:
            interval = int(interval * ease * 1.3)
        ...
    ease = max(MIN_EASE, min(ease, MAX_EASE))   # clamp: 1.3 <= ease <= 2.5
    return ease, max(1, interval)
```

**Why it's a separate, pure function.** It takes numbers, returns numbers. No
database, no `datetime.now()`. That means the tests (`tests/test_sm2.py`, plus the
`_demo()` self-check at the bottom of the file) can verify the *rules* directly:
ease never drops below 1.3, `again` resets the interval to 1, repeated `good`
grows the interval. If scheduling ever misbehaves, you debug this one small file
in isolation - no server, no client.

**The one deliberate shortcut** is marked with a `ponytail:` comment:
`MAX_EASE = 2.5` caps ease, so textbook "easy cards accelerate forever" doesn't
happen. Fine for v1; the comment tells future-you exactly what to change.

### 4.2 `state.py` - persistence over SQLite

This is the only file that touches the database. Two tables (`cards`, `reviews`),
a fresh connection per operation. The interesting method is `grade_card`:

```python
def grade_card(self, card_id, rating):
    with self._connect() as conn:
        row = conn.execute("SELECT * FROM cards WHERE id = ?", (card_id,)).fetchone()
        if row is None:
            return None
        reviews = row["reviews"] + 1
        ease, interval = schedule(row["ease"], row["interval_days"], reviews, rating)
        due = now + timedelta(days=interval)         # <- interval (days) -> a real date
        conn.execute("UPDATE cards SET ease=?, interval_days=?, due_at=?, ... WHERE id=?", ...)
        conn.execute("INSERT INTO reviews (card_id, rating, reviewed_at) VALUES (?,?,?)", ...)
    return due
```

Read that as a sentence: **load the card, ask `sm2` for the new ease/interval,
turn the interval into an actual `due_at` date, save it, and log the review.**
`state.py` owns *when* (the date math and storage); `sm2.py` owns *the rule*. That
split is the whole point.

`get_next_due_card` is just `WHERE due_at <= now ORDER BY due_at LIMIT 1` - "the
most overdue card." `get_stats` computes the streak by walking distinct review
days backward from today until there's a gap.

At the very bottom: `state = State()`. A single shared instance the tools import.
Creating it runs the schema and seeds the deck if the DB is empty.

### 4.3 `tools/` - turning functions into MCP tools

Each tool is a plain Python function. Example, `review_next.py`:

```python
def review_next(deck: Optional[str] = None) -> dict:
    """Get the next due card for review."""
    card = state.get_next_due_card(deck)
    if card is None:
        return {"message": "No cards due for review", "due": False, "due_count": 0}
    return {
        "card_id": card.id, "front": card.front, "back": card.back,
        "deck": card.deck, "due": True, "due_count": state.due_count(deck),
    }
```

Two things to notice:

- **The docstring and type hints matter.** FastMCP reads them to build the JSON
  schema the client sees - the tool's description and its `deck` parameter come
  straight from this signature. Good docstrings *are* the API here.
- **The return dict's field names are a contract.** `due`, `front`, `back`,
  `due_count` - the widget reads exactly these keys. Rename one here and the
  widget breaks. (That's half of the bug in section 6.)

### 4.4 `server.py` - the wiring (this is the MCP-specific part)

```python
mcp = FastMCP("Recall")

# The UI resource IS a prebuilt HTML file. The special mime type flags it
# as a renderable MCP App.
mcp.resource(
    uri="ui://recall/flashcard",
    mime_type="text/html;profile=mcp-app",
    ...
)(flashcard_resource)   # flashcard_resource() just reads flashcard.html off disk

mcp.tool()(ping)
mcp.tool()(add_card)
# review_next is LINKED to the UI: this is what tells a host "render the widget
# when this tool runs."
mcp.tool(app=AppConfig(resource_uri="ui://recall/flashcard"))(review_next)
mcp.tool()(grade_card)
mcp.tool()(stats)
```

This is the entire "MCP App" magic:

1. `mcp.resource(... mime_type="text/html;profile=mcp-app")` - "here is a UI."
2. `mcp.tool(app=AppConfig(resource_uri=...))` - "when `review_next` runs, the
   host should render *that* UI." The link is carried in the tool result's
   metadata as `ui.resourceUri`.

Everything else in `server.py` is transport selection:

```python
transport = os.environ.get("RECALL_TRANSPORT", "stdio")
if transport == "http":
    app = mcp.http_app(stateless_http=True, json_response=True, ...)  # + CORS
    uvicorn.run(app, host="0.0.0.0", port=int(os.environ.get("PORT", "8000")))
else:
    mcp.run(transport="stdio")
```

- **stdio** (default): the server reads/writes JSON over stdin/stdout. This is how
  local dev tools (MCP Inspector, `./dev.sh`) talk to it - no network.
- **http** (Streamable HTTP): a real web server on a port, at `/mcp`. This is what
  Render runs and what MCPJam connects to. `stateless_http=True` + `json_response`
  is the pattern the official MCP Apps example uses, and it sidesteps a Claude
  proxy bug (#636) with GET event-streams. CORS is added so browser-based hosts
  can connect cross-origin.

### 4.5 `flashcard.html` - the widget

One self-contained file: styles, markup, and a `<script>`. The script has two parts.

**A) The bridge** - how the iframe talks to the host. The ext-apps protocol is
**JSON-RPC 2.0 over `postMessage`**:

```javascript
callTool(name, args) {
    const id = nextId++;
    return new Promise((resolve, reject) => {
        pending.set(id, { resolve, reject });
        window.parent.postMessage({
            jsonrpc: '2.0', id,
            method: 'tools/call',
            params: { name, arguments: args || {} },
        }, '*');                      // -> up to the host, which forwards to your server
    });
}
```

The host also *pushes* the opening card to the widget as a notification
(`ui/notifications/tool-result`) so the card shows instantly without the widget
having to ask.

**B) The view controller** - `app.showCard()` fills in the front text and shows
the grade buttons; `app.flip()` swaps front/back; `app.grade(rating)` calls
`grade_card` then `review_next` to advance:

```javascript
async grade(rating) {
    await bridge.callTool('grade_card', { card_id: this.card.card_id, rating });
    const next = structured(await bridge.callTool('review_next', {}));
    this.render(next);        // show the next card, or finish
}
```

Notice: **grading never involves the LLM.** The button calls a tool directly
through the host. No model, no tokens.

## 5. One full request, traced

This is the artifact diagram in words. "quiz me" -> a graded card:

1. **You -> client:** "quiz me".
2. **The client's model picks a tool:** calls `review_next`. *(This is the LLM's
   only involvement.)*
3. **Server -> client:** returns the due card **plus** `ui.resourceUri` pointing
   at `ui://recall/flashcard`.
4. **Client fetches the HTML** for that resource from your server.
5. **Client renders it** in a sandboxed iframe and pushes the card data via
   `ui/notifications/tool-result`.
6. **-> The LLM is now out of the loop.**
7. **You click the card:** it flips locally (no network).
8. **You click "Good":** the widget calls `grade_card` -> host -> server. SM-2
   reschedules, a review is logged.
9. **The widget calls `review_next`** for the next card. Repeat from step 7.

## 6. The bug we fixed (a good teaching case)

The widget rendered "Session Complete! / No cards due!" even with 20 cards due.
Two causes, both instructive:

1. **Payload shape.** `structured()` only knew how to read one wrapper
   (`result.structuredContent`). Different hosts wrap tool results differently -
   MCPJam's *notification* payload didn't match, so extraction returned `{}`.
2. **A too-eager `else`.** `render()` did `if (data.due) showCard(); else finish()`.
   An empty `{}` has no `due`, so it fell into `finish()` - the "no cards" screen -
   even though a *second* delivery path had already rendered the real card. Two
   paths, one good, one wrongly calling `finish()`.

The fix (in `flashcard.html`):

```javascript
// 1) understand more payload shapes, incl. a bare object
function structured(result) {
    if (!result || typeof result !== 'object') return {};
    return result.structuredContent
        || (result.result && result.result.structuredContent)
        || result;
}

// 2) only finish when the server EXPLICITLY says nothing is due
render(data) {
    if (data && data.due) this.showCard(data);
    else if (data && data.due === false) this.finish();
    // empty/unknown payload -> leave the view alone; the other path renders it
}
```

**Lesson:** at a trust/format boundary (a message from another system), be liberal
in what you accept and conservative about destructive actions. "I didn't
understand this message" must not mean "declare the session over."

## 7. How to see it again

**Locally, in the official renderer:**
```bash
cd server
RECALL_TRANSPORT=http PORT=8000 uv run python src/server.py    # start the server
# in another terminal:
cd ext-apps/examples/basic-host
SERVERS='["http://localhost:8000/mcp"]' npx tsx serve.ts        # start the host
# open http://localhost:8080 and call review_next
```

**Against the live deploy, in MCPJam:**
```bash
npx -y @mcpjam/inspector@latest        # opens http://127.0.0.1:6274
```
Add a Streamable HTTP server: `https://recall-mcp-wa3n.onrender.com/mcp`, go to
Playground, Run `review_next`. (MCPJam's built-in model is free - it's on MCPJam's
account, not yours.)

**Run the tests / SM-2 self-check:**
```bash
cd server
uv run pytest
uv run python src/sm2.py     # prints "sm2 self-check OK: [...]"
```

## 8. Where the widget renders (host reality)

Not every client is an MCP Apps *host*. Tested:

- **basic-host** (official ext-apps renderer): renders + interactive. Proven.
- **MCPJam**: renders + interactive against the live server. Proven.
- **Claude.ai web (custom connector)**: tool calls work, but the widget does **not**
  render - a Claude-side custom-connector limitation (bug #636), not your code.
- **Hermes**: no MCP Apps support at all (markdown/mermaid only).

Bottom line: the app is correct and deployed; *which chat surface* renders a
custom-connector widget is an ecosystem limitation, not a gap in Recall.
